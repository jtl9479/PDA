## 4. 전환 위험 요소 분석

### 4.1 최고 위험 (Critical)

#### 4.1.1 프론트엔드 비즈니스 로직 매몰

> **위험도: ★★★★★ (5/5)**

**현황:**
- 636개 XFDL 화면에 **약 65~70%의 비즈니스 로직**이 내장되어 있음
- 전체 151,824 라인의 프론트엔드 코드에 유효성 검증, 계산 로직, 조건부 표시, 데이터 변환 로직 혼재
- gfn* 글로벌 함수 12,000회+ 호출 — Nexacro 전용 API

**구체적 위험:**
- XFDL 내 `<Script>` 섹션에 묻혀있는 업무 로직을 누락할 가능성
- 회계 전표 입력 화면(A0101_chitIns_pu.xfdl) 같은 복잡 화면은 1,493라인에 12개+ 데이터셋, 70개+ 동적 입력 필드 포함
- 동적 그리드 컬럼 생성(P0301.xfdl), 피벗 데이터 변환 등 고급 로직
- 조건부 셀 편집/표시 로직이 Grid `expr:` 속성에 내장

**대응 방안:**
- XFDL 파일별 스크립트 추출 → 로직 카탈로그 문서화 선행
- 화면별 복잡도 등급(상/중/하) 분류 후 단계적 전환
- 핵심 업무 로직은 백엔드(Service)로 이관하여 중복 제거

---

#### 4.1.2 ERP 데이터 정합성 위험

> **위험도: ★★★★★ (5/5)**

**현황:**
- ERP 시스템은 회계, 세금계산서, 급여 등 법적 효력이 있는 데이터를 처리
- 전환 과정에서 계산 로직 1개라도 오류 시 회계 부정합 발생 가능
- 현행 시스템에 테스트 코드가 1개뿐(ErpApplicationTests.java — 빈 테스트)

**구체적 위험:**
- 소수점 반올림/절사 차이 (BigDecimal 처리)
- 세금 계산 로직 차이
- 일자 계산 (영업일, 결산일 등) 로직 차이
- 다중 사업장 데이터 분리 오류
- Nexacro의 Dataset 필터링/정렬이 DB 쿼리와 다른 결과를 낼 가능성

**대응 방안:**
- 전환 전 현행 시스템의 주요 업무 플로우별 테스트 데이터셋 확보
- 양 시스템 병행 운영 기간 설정 (최소 1~2개월)
- 회계 모듈은 결산 기간 이후 전환 (연말/반기 결산 후)

---

#### 4.1.3 Nexacro Grid → AG Grid 기능 격차

> **위험도: ★★★★☆ (4/5)**

**현황:**
- Nexacro Grid는 한국형 ERP에 특화된 고급 기능 다수 보유:
  - 동적 컬럼 생성/삭제
  - 셀 병합 (rowspan/colspan)
  - 조건부 셀 편집 타입 변경 (`expr:` 기반)
  - 요약행(Summary Row) 자동 계산
  - Combo/Calendar/MaskEdit 셀 내장
  - 멀티 레벨 헤더밴드
  - 행 단위 CRUD 상태 추적 (INSERT/UPDATE/DELETE)

**구체적 위험:**
- AG Grid Community는 일부 고급 기능 미지원 (Enterprise 라이선스 필요)
- Nexacro의 `expr:` 기반 조건부 렌더링은 AG Grid에서 cellRenderer로 재구현 필요
- Dataset의 `getRowType()` 기반 행 상태 추적 패턴은 별도 구현 필요
- 동적 피벗 그리드(P0301.xfdl) 수준의 복잡 그리드 재현 난이도 높음

**대응 방안:**
- AG Grid Enterprise 라이선스 도입 권장 (피벗, 그룹핑, 서버사이드 모델)
- 공통 Grid Wrapper 컴포넌트를 먼저 개발하여 CRUD 상태 추적 패턴 표준화
- 복잡 그리드 화면은 별도 PoC(개념 증명) 선행

#### 4.2.3 Spring Boot 2.7 → 3.x 동시 업그레이드

> **위험도: ★★★☆☆ (3/5)**

**현황:**
- 현행: Spring Boot 2.7.4, JDK 1.8
- Spring Boot 2.7은 2023년 11월 EOL(지원 종료)
- JDK 8도 공식 지원 종료 임박

**구체적 위험:**
- javax → jakarta 네임스페이스 전환 (모든 import 변경)
- Spring Security 설정 방식 변경 (WebSecurityConfigurerAdapter 폐기)
- Hibernate 5 → 6 마이그레이션
- 일부 라이브러리 호환성 문제 가능

**대응 방안:**
- 프론트엔드 전환과 Spring Boot 업그레이드를 동시에 진행하면 위험 증가
- **권장: 프론트엔드 전환 완료 후 → Spring Boot 업그레이드 순차 진행**
- 또는 Spring Boot 업그레이드를 먼저 수행 후 프론트엔드 전환

#### 4.3.2 인증/보안 전환

> **위험도: ★★★☆☆ (3/5)**

- 현행 JWT 토큰이 Nexacro 헤더 방식으로 전달
- SHA1 비밀번호 해싱 (보안 취약, 전환 기회)
- 사용자 역할(SUPER/ADMIN/USER) 체계 유지 필요

**대응 방안:**
- JWT 토큰을 표준 Authorization: Bearer 헤더로 전환
- 비밀번호를 BCrypt로 점진 마이그레이션 (로그인 시 자동 재해싱)
- Spring Security 6.x 설정으로 현대화

## 8. 핵심 권고 사항

### 8.1 반드시 해야 할 것 (Must)

1. **파일럿 먼저**: co(기초정보) 모듈로 전환 PoC 진행 후 본격 착수
2. **공통 컴포넌트 완성도 확보**: 업무 화면 전에 공통 컴포넌트 충분히 검증
3. **XFDL 스크립트 로직 카탈로그**: 636개 화면의 내장 로직을 사전 문서화
4. **병행 운영 환경**: 전환 기간 중 기존/신규 시스템 동시 접근 가능하게 구성
5. **회계 모듈은 결산 이후**: 연간/반기 결산 완료 시점에 맞춰 전환

### 8.2 하면 좋은 것 (Should)

1. **AG Grid Enterprise 라이선스**: 피벗, 그룹핑, 서버사이드 모델 필요
2. **Storybook 도입**: 공통 컴포넌트 독립 테스트/문서화
3. **API 버전 관리**: 기존 API 유지하면서 신규 REST API 병행 제공
4. **CI/CD 파이프라인**: 자동 빌드/배포 환경 구축

### 8.3 하지 말아야 할 것 (Must Not)

1. **빅뱅 전환 금지**: 전체 모듈 동시 전환은 절대 금지 → 모듈별 점진 전환
2. **DB 스키마 동시 변경 금지**: 프레임워크 전환과 DB 변경을 동시에 하지 않음
3. **AI 생성 코드 무검수 배포 금지**: 반드시 코드 리뷰 후 머지
4. **백엔드+프론트엔드 동시 전환 금지**: 프론트엔드 우선, 백엔드 이후 순차 진행
