## 이슈/메모

- **원복 사유** — 개발66·67 의 "searchType별 파일 분리"는 공통 로직 추상화가 아니라 **타입별 전체 복사**로 귀결됐다. 타입 파일 8개가 서로 **78~91% 동일**(WholesaleType ↔ EmartNonfixedType 차이 80줄 / LotteType ↔ EmartNonfixedType 차이 213줄)하여, 한 줄 수정에 8곳을 고쳐야 하는 구조가 됐다.
- **규모 역전** — 원본 Activity 3,739줄 → 원복 직전 Activity 2,278줄 + type 7,373줄 = **9,651줄(2.6배)**. 프로젝트 목적 "4. 소스 정리"와 정반대 결과.
- **검증 미수행** — 개발66 Step 14 · 개발67 Step 10(실기기 통합 테스트)이 **한 번도 수행되지 않은 상태**였다. 기능 100% 동일 보장이 없는 시점이라 원복 비용이 가장 낮았다.
- **재설계 시 주의** — 다시 분리할 경우 ① 공통 부모/템플릿 메서드로 중복을 먼저 제거할 것 ② searchType 0↔4(7곳), 2↔5(3곳) 차이는 플래그로 묶이지 않음(개발66 §1.3 판정은 유효) ③ 각 Step 후 실기기 검증을 뒤로 미루지 말 것
- **원복 이력 참조** — 분리 코드가 필요하면 `git show 1a725ac` 이전 이력에 전부 남아 있다(커밋 `dc3e4d3`~`52c3258`).
- **소스 정리 순서** — 사용자 결정에 따라 **로직 영향이 없는 항목부터** 진행한다. 분리 방식 재설계는 그 이후.
- **문서 번호 66 재사용** — 폐기된 `66`(클래스 분리) 번호를 소스 정리 문서가 재사용한다. 원본 66·67 내용은 git 이력(`dc3e4d3`~`52c3258`)에 남아 있다.
- **후속 후보(지시 대기)** — ① 미사용 import 7개(`IOException`·`DecimalFormat`·`ParseException`·`SimpleDateFormat`·`Calendar`·`Date`·`Set`) ② 클래스 Javadoc searchType 표 오류(4·5·6 실제와 불일치, 2·7 누락, "Woosim" 표기) ③ 참조 0건 `BixolonShipmentActivity_back.java` 3,730줄
- **Step 2 작업 중 정정** — 섹션 삭제 후 빈 줄을 파일 전역으로 축소해 무관한 빈 줄 5곳(483·1954·2248·2581·2834)과 EOF 빈 줄이 함께 지워졌다. 되돌린 뒤 **삭제 구간 인접 빈 줄만** 제거하도록 고쳐 재적용했다. 일괄 치환 시 적용 범위를 변경 구간으로 한정할 것

- **나머지 파일은 하나씩** — 사용자 결정. `ShipmentActivity`·`MainActivity`·`LabelPrintHelper` 중복 선언, `ProgressDlgShipSearch`(13)·`ProgressDlgBarcodeSearch`(8)·`ProgressDlgGoodsWetSearch`(1)·`ShipmentListAdapter`(1) 리터럴 비교 23곳
- **죽은 코드 판정 기준** — "살아있는 호출"만 센다(`//` 주석 호출부 제외). 삭제 전 **원본 `D:\PDA\PDA-INNO(원본)` 에서도 죽어 있는지 반드시 대조**한다. Step 8 4건은 전부 원본부터 죽어 있었다
- **오탐 주의** — `onKey` 는 정적 호출 0건이지만 `setOnKeyListener` 로 등록된 프레임워크 콜백이라 살아있다. Android 콜백은 호출 수로 판정하면 안 된다
- **`setBarcodeMsg`(404줄) 분리 검토 결과** — 메서드만 빼면 Activity 필드 164회 참조가 그대로 따라오고(개발66 재현), 필드까지 빼려 해도 **전용인 것이 0/24**(`arSM` 30:179, `current_work_position` 31:83). 유효한 안은 `WeighingState`(순수 데이터) + 콜백 인터페이스인데 치환 약 350곳 + 실행 코드 재작성이라 **실기기 기준선 확보 후** 착수한다. View 객체(Spinner·EditText·ListView·Vibrator)는 누수 위험으로 Activity 밖으로 빼지 않는다. static `Common` 에 화면 상태를 두는 것도 금지(Activity 재진입 시 잔존)
- **`ShipmentActivity.java` 유지 확정** — 진입 경로 0건인 죽은 파일이나 사용자 판단으로 **삭제하지 않는다**. 정리 대상에서도 제외(도메인 상수 33개 중복 포함)
- **익명 내부 클래스에서의 `this`** — `hideKeyboard()` 호출부 4곳이 전부 `View.OnClickListener`/`OnKeyListener` 익명 클래스 안이라 `this` 가 익명 클래스를 가리킨다. `Common.hideKeyboard(BixolonShipmentActivity.this)` 처럼 바깥 클래스를 명시해야 한다
- **메서드 결합도 전수 측정 결과** — 분리 가능한 것은 상품 판정 계열 4개(`find_work_info` 67 / `find_work_info_barcodeGoods` 47 / `find_PackerProduct` 16 / `find_PackerProductBarcodeGoods` 16, **합 146줄**). Activity 필드를 `edit_product_name`·`edit_product_code` 2개만 쓰고 `arSM`·`current_work_position` 을 전혀 안 건드린다. 반대로 `wet_data_insert`(결합 107회)·`setBarcodeMsg`(97)·`show_wetDetailDialog`(View 19종 46회)·`onCreate`(View 23종 51회)는 분리 불가
- **미사용 인스턴스 필드 발견** — `makingdateInputFlag`(283)는 원본 `ShipmentActivity.java:135` 부터 선언만 있고 읽기·쓰기 0건. `private static final` 이 아니라 Step 2 상수 검사에 안 걸렸다
- **상수·메서드 배치 기준 확립** — `Common`=**값**(설정·상수·전역 상태), `CommonUtils`=**동작**(여러 Activity 공통 함수, `Activity`/`Context` 받음), 업무 로직은 **전용 클래스**(상품 판정 `find_*` → `BarcodeMatcher` 예정). 계기: `hideKeyboard()` 를 `Common` 에 넣자 `android.app.Activity`·`Context`·`InputMethodManager` import 가 생겨 설정 클래스가 UI 프레임워크에 의존하게 됨
- **주석이 코드를 베끼면 반드시 낡는다** — Javadoc 328줄(파일의 10%) 중 상당수가 분기·흐름을 그대로 옮겨 적고 있었고, 실제로 `ProgressDlgShipmentSend`(존재하지 않는 `homeplus.jsp` 분기 서술)·`mHandler`(죽은 `MESSAGE_*` 설명)가 사실과 달랐다. 요약·주의만 남기고 흐름 나열은 제거한다
- **"이동됨" 주석 주의** — `// SLCS 헬퍼 메서드 → LabelPrintHelper로 이동됨` 이라 써놓고 바로 아래 8개가 그대로 있었다. 실제로는 이동이 아니라 **복사**였고 한쪽(`slcsBarcode`)만 수정돼 본문이 갈라져 있었다(`BD` vs `B1`). 이런 주석은 사실 확인 후 처리
- **주석의 줄 번호는 쓰지 않는다** — `weight list printing(4143, 4188줄)` 이 실제 2847·2887 과 달랐다. 위치 대신 메서드명으로 표기

- **정리 완료 현황** — 호출 0건 메서드 0개 / 미사용 필드 0개 / 주석 처리된 코드 0줄. Javadoc 328 → 약 120줄
