# PDA 데이터 동기화 시나리오

**작성일**: 2026-02-04
**관련 파일**: `ProgressDlgShipSearch.java`

---

## 1. 개요

PDA 앱에서 "대상받기" 버튼 클릭 시 서버(VIEW)와 로컬 DB(TB_SHIPMENT)를 동기화하는 로직입니다.

---

## 2. 기능 목적

### 2.1 핵심 목적

**대상받기를 다시 실행했을 때, 서버에서 이미 처리 완료되거나 취소된 항목을 PDA에서도 제거하여 "미처리 대상만" 리스트에 남기기 위함**

### 2.2 동작 예시

```
[1차 대상받기 - 오전 9시]
서버: A, B, C, D, E (5건)
PDA 저장: A, B, C, D, E (5건)

[작업 진행]
A, B 계근 완료 → 서버에 전송 → 서버에서 완료 처리됨

[2차 대상받기 - 오전 11시]
서버 조회: C, D, E (3건) ← 완료된 A, B는 조회 안됨
PDA 기존: A, B, C, D, E (5건)

[동기화 결과]
- 삭제: A, B (이미 완료됨)
- 유지: C, D, E (미처리)

최종 PDA: C, D, E (3건) ← 미처리 대상만 남음
```

### 2.3 삭제 대상 판단 기준

| 상황 | 서버 상태 | PDA 처리 |
|------|----------|----------|
| 계근 완료 | VIEW에서 제외 | 삭제 |
| 출하 취소 | VIEW에서 제외 | 삭제 |
| 미처리 | VIEW에 존재 | 유지 |

**→ 항상 "현재 처리해야 할 대상"만 PDA에 남도록 동기화**

## 4. 동기화 로직

### 4.1 변수 설명

| 변수 | 설명 |
|------|------|
| `list_si_pda` | PDA 로컬 DB에 **이미 저장된** 출하대상 리스트 |
| `list_si_info` | 서버(JSP)에서 **새로 받아온** 출하대상 리스트 |
| `list_delete` | 삭제 대상 (PDA에 있고 서버에 없음) |
| `list_insert` | 추가 대상 (서버에 있고 PDA에 없음) |

### 4.2 비교 로직

```java
// 1. 로컬 DB 기존 데이터 조회
ArrayList<Shipments_Info> list_si_pda = DBHandler.selectqueryAllShipment(mContext);

// 2. 서버에서 데이터 다운로드 → list_si_info

// 3. 삭제 대상 검색 (PDA에 있고 서버에 없음)
for (int i = 0; i < list_si_pda.size(); i++) {
    int check = 0;
    for (int j = 0; j < list_si_info.size(); j++) {
        if (list_si_pda.get(i).getGI_D_ID().equals(list_si_info.get(j).getGI_D_ID())) {
            check++;
            break;
        }
    }
    if (check == 0) {
        list_delete.add(list_si_pda.get(i).getGI_D_ID());  // 삭제 대상
    }
}

// 4. 추가 대상 검색 (서버에 있고 PDA에 없음)
for (int i = 0; i < list_si_info.size(); i++) {
    int check = 0;
    for (int j = 0; j < list_si_pda.size(); j++) {
        if (list_si_info.get(i).getGI_D_ID().equals(list_si_pda.get(j).getGI_D_ID())) {
            check++;
            break;
        }
    }
    if (check == 0) {
        list_insert.add(list_si_info.get(i));  // 추가 대상
    }
}

// 5. DB 동기화 실행
DBHandler.refreshShipmentList(mContext, list_delete, list_insert);
```

## 5. 삭제 대상 발생 시나리오

### 5.1 시나리오 1: 출하 취소

```
[1일차 - 오전 9시]
사용자: "대상받기" 버튼 클릭
서버 VIEW 조회 결과: A, B, C, D, E (5건)
PDA 로컬 DB 저장: A, B, C, D, E (5건)

[1일차 - 오전 10시]
관리자가 서버에서 출하건 C, D 취소 처리

[1일차 - 오전 11시]
사용자: "대상받기" 버튼 다시 클릭
서버 VIEW 조회 결과: A, B, E (3건) ← C, D 없음
PDA 로컬 DB 기존: A, B, C, D, E (5건)

비교 결과:
- PDA에 있고 서버에 없음: C, D → 삭제 대상
- 서버에 있고 PDA에 없음: 없음 → 추가 대상 없음

최종 PDA 로컬 DB: A, B, E (3건)
```

## 6. 추가 대상 발생 시나리오

### 6.1 기능 목적

**서버에 새로 생긴 출하대상을 PDA 로컬 DB에 추가하는 로직입니다.**

### 6.2 시나리오 1: 처음 대상받기

```
[최초 실행]
PDA 로컬 DB: (비어있음)
서버 VIEW: A, B, C, D, E (5건)

비교 결과:
- 서버에 있고 PDA에 없음: A, B, C, D, E → 전체 추가 대상

최종 PDA: A, B, C, D, E (5건)
```

### 6.3 시나리오 2: 서버에서 신규 출하건 추가

```
[1차 대상받기 - 오전 9시]
서버: A, B, C (3건)
PDA 저장: A, B, C (3건)

[오전 10시]
관리자가 서버에서 신규 출하건 D, E 등록

[2차 대상받기 - 오전 11시]
서버 조회: A, B, C, D, E (5건)
PDA 기존: A, B, C (3건)

비교 결과:
- 서버에 있고 PDA에 없음: D, E → 추가 대상
- 양쪽에 존재: A, B, C → 유지

최종 PDA: A, B, C, D, E (5건)
```

### 6.4 시나리오 3: 날짜/창고 변경 시

```
[삼일냉장 → SWC 변경]
PDA 기존: A, B (삼일냉장 데이터)
서버 조회: X, Y, Z (SWC 데이터)

비교 결과:
- PDA에 있고 서버에 없음: A, B → 삭제 대상
- 서버에 있고 PDA에 없음: X, Y, Z → 추가 대상

최종 PDA: X, Y, Z (3건)
```

### 6.5 추가 대상 요약

| 구분 | 의미 | 처리 |
|------|------|------|
| **삭제 대상** | 완료/취소된 항목 | PDA에서 제거 |
| **추가 대상** | 신규 출하건 | PDA에 저장 |

**→ 두 로직이 함께 동작하여 PDA를 서버 최신 상태로 동기화합니다.**

## 8. 처음 작동 시

PDA 앱 최초 실행 시에도 정상 동작합니다.

| 변수 | 상태 |
|------|------|
| `list_si_pda` | 빈 ArrayList (size = 0) |
| `list_si_info` | 서버에서 받은 데이터 |

**결과:**
- 삭제 대상: 없음 (list_si_pda가 비어있음)
- 추가 대상: 서버 데이터 전체

→ 서버에서 받은 모든 데이터가 로컬 DB에 INSERT됨

## 9. 로컬 DB 기반 작업

### 9.1 개요

**동기화 완료 후, 안드로이드 앱의 모든 작업은 로컬 DB(SQLite) 데이터를 기반으로 진행됩니다.**

### 9.2 데이터 사용 구조

```
┌─────────────────────────────────────────────────────────────────┐
│                         서버                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  VW_PDA_WID_LIST (VIEW)                                  │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼ "대상받기" (1회)
┌─────────────────────────────────────────────────────────────────┐
│                      PDA 로컬 DB (SQLite)                        │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  TB_SHIPMENT (출하대상)                                   │   │
│  │  TB_BARCODE_INFO (바코드정보)                             │   │
│  │  TB_GOODS_WET (계근결과)                                  │   │
│  └─────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼ 계근 작업 시 (반복)
┌─────────────────────────────────────────────────────────────────┐
│                      안드로이드 앱 화면                           │
│  - 출하대상 리스트 조회                                          │
│  - 바코드 스캔/검증                                              │
│  - 계근 처리                                                     │
│  - 라벨 출력                                                     │
└─────────────────────────────────────────────────────────────────┘
```

### 9.3 작업 흐름

| 단계 | 동작 | 데이터 소스 |
|------|------|------------|
| 1 | 대상받기 | 서버 → 로컬 DB 저장 |
| 2 | 출하대상 리스트 표시 | **로컬 DB** |
| 3 | 바코드 스캔/검증 | **로컬 DB** |
| 4 | 계근 처리 | **로컬 DB** |
| 5 | 라벨 출력 | **로컬 DB** |
| 6 | 결과 전송 | 로컬 DB → 서버 |

### 9.4 이 구조의 장점

| 장점 | 설명 |
|------|------|
| **오프라인 작업 가능** | 네트워크 끊겨도 계근 작업 진행 가능 |
| **빠른 응답 속도** | 매번 서버 조회 없이 로컬에서 즉시 처리 |
| **네트워크 부하 감소** | 대상받기 1회 + 결과전송 1회만 통신 |
| **작업 안정성** | 중간에 앱 종료되어도 데이터 유지 |

### 9.5 서버 통신 vs 로컬 DB 사용

```
[서버 통신]                    [로컬 DB 사용]
    │                              │
    ▼                              ▼
 대상받기 (시작)              계근 작업 (반복)
 결과전송 (종료)              리스트 조회
                              바코드 검증
                              라벨 출력
```

**→ 서버 통신은 시작/종료 시에만, 실제 작업은 모두 로컬 DB 기반으로 진행**
