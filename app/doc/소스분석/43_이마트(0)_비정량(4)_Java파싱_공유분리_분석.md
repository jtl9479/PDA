# 이마트(0)_비정량(4) Java파싱 공유분리 분석

**작성일**: 2026-04-07
**목적**: searchType "0"(이마트)과 "4"(비정량)의 Java 파싱 로직이 공유 구조를 유지해야 하는지 분리해야 하는지 판정

---

## AI 제약 조건

- 기존 WHERE 조건, 로직을 임의로 제거/추가/변경하지 않는다
- 문서에 명시된 step만 진행하고, 다음 step은 지시를 기다린다
- step 완료 후 체크리스트 + 진행 현황을 반드시 업데이트한다
- 문서에 없는 개선/리팩토링을 임의로 수행하지 않는다
- 기존 기능과 100% 동일하게 동작해야 한다

## 1. 원본 파싱 구조 (Oracle)

- 모든 searchType 공통: temp[0]~temp[31] (32개)
- searchType "0"||"4" 공유: temp[32]~temp[37] (6개 추가)
- 합계: **38개 필드 100% 동일 파싱**

## 2. 현재 파싱 구조 (MSSQL 전환 후)

- 모든 searchType 공통: temp[0]~temp[23] (24개)
- searchType "0"||"4" 공유: temp[24]~temp[30] (7개 추가)
- 합계: **31개 필드 100% 동일 파싱**

## 4. 판정: 공유 유지

### 근거

1. 컬럼 개수 동일 (31개)
2. 컬럼 순서 동일
3. 컬럼 별칭 동일
4. 차이는 SQL 레벨(VIEW/JSP 내부 쿼리)에서만 발생
5. 원본(Oracle)도 공유 구조로 운영

### 결론

- **분리 불필요**
- Java 파싱 코드(ProgressDlgShipSearch)에서 searchType "0"||"4" 공유 구조를 그대로 유지한다

## 5. WHERE 조건 차이 (JSP 레벨)

| 조건 | 이마트 (searchType=0) | 비정량 (searchType=4) |
|------|----------------------|----------------------|
| 타입구분 | 'W' | IN('J','B') |
| 바코드타입 | 없음 | 'M8' |
| URL | search_emart.jsp 계열 | search_non_quantity.jsp 계열 |

- PDA Java에서는 searchType별 다른 URL을 호출하여 분기됨
- 파싱 로직 자체는 동일하며, 서버(JSP)에서 WHERE 조건으로 데이터를 구분
