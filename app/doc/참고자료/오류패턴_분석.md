# 오류 패턴 분석 (이마트 searchType=0 전환 기준)

## 목적
- 이마트(searchType=0) 전환 중 발견된 오류를 패턴별로 분류
- 다른 searchType(홈플러스, 도매, 롯데, 비정량 등) 전환 시 동일 패턴 사전 체크용
- 서브 에이전트(error-doc, code-verifier)가 참조하여 사전 탐지 가능하도록

---

## 1. 패턴 분류

| 패턴 | 설명 | 건수 |
|:----:|------|:----:|
| **A** | DB 타입 불일치 (Oracle MSSQL 타입 차이) | 5건 |
| **B** | 테이블/VIEW 미존재 (Oracle 테이블이 MSSQL에 없음) | 1건 |
| **C** | 컬럼명/구조 변경 (Oracle MSSQL 컬럼 전환) | 10건 |
| **D** | ID 비유니크 (GI_D_ID 등 데이터 구조 차이) | 5건 |
| **E** | 기기 전환 (PDA/프린터 하드웨어 변경) | 3건 |
| **F** | UI/로직 버그 (기존 코드 문제 또는 신규 코드 문제) | 9건 |
| **G** | 인코딩/파싱 (데이터 전송/파싱 구조 문제) | 4건 |

---

## 2. 패턴별 오류 목록

### 패턴 A: DB 타입 불일치

Oracle에서 정수로 내려오던 값이 MSSQL에서 FLOAT 등 다른 타입으로 내려오면서 Java 파싱 오류 발생.

| 오류 번호 | 오류명 | 핵심 원인 | 재발 가능성 |
|:---------:|--------|-----------|:----------:|
| 14 | GI_REQ_PKG FLOAT parseInt 오류 | MSSQL FLOAT 타입이 "2.0"으로 내려와 Integer.parseInt 에러 | **높음** |
| 19 | SM_출고계근 회사코드 ITEM_CODE 잘림 오류 | packet 컬럼 매핑 오류 + VARCHAR(2)에 10자리 데이터 INSERT | **높음** |
| 22 | STORE_IN_DATE datetime 형식 변환 누락 | MSSQL datetime 컬럼을 CONVERT 없이 SELECT → rs.getString()이 타임스탬프 전체 반환 | **높음** |
| 26 | GI_REQ_PKG null parseDouble 예외 | SM_출고LOT.박스수량 NULL 허용 시 "null" 문자열 parseDouble → NumberFormatException | **높음** |
| 34 | 홈플러스 STORE_IN_DATE datetime CONVERT 미적용 (라벨 날짜 오인쇄) | search_shipment_homeplus.jsp:59 SD.납기일자 CONVERT 미적용 → LabelPrintHelper.java:1177 substring(0,4)/(4,6)/(6,8) 파싱 오류. 22번과 동일 원인, 이마트에서 수정된 패턴이 홈플러스에 미반영 | **높음** |

**공통 특징**: MSSQL 컬럼 타입(FLOAT, VARCHAR 크기, datetime, NULL 허용)과 Java 파싱/INSERT 로직 불일치.

---

### 패턴 B: 테이블/VIEW 미존재

Oracle 시절 사용하던 테이블이 MSSQL에 존재하지 않음.

| 오류 번호 | 오류명 | 핵심 원인 | 재발 가능성 |
|:---------:|--------|-----------|:----------:|
| 20 | update_shipment W_GOODS_ID 미존재 | Oracle W_GOODS_ID 테이블이 MSSQL에 없음, SM_출고상세로 대체 필요 | **높음** |

**공통 특징**: JSP에서 Oracle 테이블명을 그대로 사용하여 MSSQL에서 오류 발생.

---

### 패턴 C: 컬럼명/구조 변경

Oracle에서 MSSQL로 전환하면서 테이블 구조, JOIN 방식, 컬럼 매핑이 변경되어 조회 누락 또는 오류 발생.

| 오류 번호 | 오류명 | 핵심 원인 | 재발 가능성 |
|:---------:|--------|-----------|:----------:|
| 04 | 매출처품목코드매핑 최상위거래처 조회누락 | CO_매출처품목코드매핑 JOIN 시 최상위 거래처 미고려 | **높음** |
| 08 | M0라벨 창고구역표시 원본과 불일치 | 원본에 없는 WH_AREA가 라벨에 표시됨 (컬럼 매핑 차이) | **중간** |
| 09 | 소스정합성체크 컬럼누락 미설정 | INSERT에 REG_DATE/REG_TIME/MEMO 누락, BOX_ORDER/CLIENT_TYPE 미설정 | **낮음** |
| 12 | 출하대상팝업 중량수량 LEFT JOIN 중복합산 | TB_GOODS_WET LEFT JOIN으로 TB_SHIPMENT 행 중복, SUM 뻥튀기 | **중간** |
| 21 | 비정량 이마트 EMARTLOGIS_CODE 빈 문자열 라벨 출력 예외 | Oracle DECODE(NULL→'0000000') 처리가 MSSQL 전환 시 COALESCE로 대체되면서 빈 문자열 미방어 → StringIndexOutOfBoundsException | **높음** |
| 23 | TB_BARCODE_INFO INSERT REG_DATE/REG_TIME/MEMO 누락 | CREATE TABLE에 존재하나 INSERT SQL에서 누락 → NULL 저장 (무증상 데이터 손실) | **낮음** |
| 25 | 출하대상 조회 행중복 — 월품목별재고화일LOT별VIEW 년월조건 누락 | LEFT JOIN 년월 조건 없어 동일 LOT이 다월 재고행 수만큼 중복 → 계근수량 부풀림 | **높음** |
| 27 | PPCODE 컬럼명 대소문자 불일치 | JSP에서 ppCode(소문자)와 PPCODE(대문자) 혼용 → MSSQL CS 콜레이션 환경에서 컬럼 미발견 오류 | **중간** |
| 32 | 홈플러스 월품목별재고 V뷰 년월조건 누락 (출하대상 행중복) | search_shipment_homeplus.jsp:93~98 LEFT JOIN에 년월 조건 없음. 25번과 동일 원인, 이마트에서 수정된 패턴(커밋 dce6722)이 홈플러스에 미반영 | **높음** |
| 33 | 홈플러스 SM_수주상세 LEFT JOIN 다중행 팽창 (출하 건 중복) | search_shipment_homeplus.jsp:99~100 단순 LEFT JOIN, 마트사SEQ 1:N 매칭 시 Cartesian product | **높음** |

**공통 특징**: Oracle VIEW/테이블 구조를 MSSQL로 전환하면서 JOIN 방식, 컬럼 누락, 매핑 불일치 발생.

### 패턴 D: ID 비유니크 (GI_D_ID 구조 차이)

Oracle에서 LOT별로 고유했던 GI_D_ID가 MSSQL에서는 SM_출고상세.SEQ 기준이라 LOT별로 중복됨.

| 오류 번호 | 오류명 | 핵심 원인 | 재발 가능성 |
|:---------:|--------|-----------|:----------:|
| 15 | GI_D_ID LOT별 미분리 계근수량 중복표시 | 같은 품목에 LOT 여러개면 GI_D_ID 동일 → 계근수량 중복 | **높음** |
| 16 | GI_D_ID 비유니크 전체 영향범위 | GI_D_ID를 유니크 식별자로 사용하는 약 41곳 영향 | **높음** |
| 17 | GI_L_ID 단독사용시 사이드이펙트 | GI_D_ID 제거 시 서버 전송/조회에서 치명적 오류 3건 발생 | **높음** |
| 18 | refreshShipmentList AND/OR 연산자 버그 | 삭제 대상 2건 이상 시 AND 연결로 삭제 0건 | **낮음** |
| 35 | 홈플러스 GI_L_ID 미전송/미파싱 (GI_D_ID 비유니크) | search_shipment_homeplus.jsp GI_L_ID SELECT/전송 없음, ProgressDlgShipSearch.java:263~286 searchType="2" 파싱 분기 없음. 15/16/17번과 동일 원인, 이마트에서 GI_L_ID 추가로 해결한 패턴(개발/31)이 홈플러스에 미반영. 실운영 재현 여부는 ERP 데이터 추가 확인 필요 | **확인 필요** |

**공통 특징**: Oracle→MSSQL 전환 시 테이블 구조(출고상세/출고LOT 분리)가 달라 식별자 유니크성 깨짐. 앱 전반에 걸쳐 GI_D_ID + GI_L_ID 조합으로 수정 필요.

### 패턴 E: 기기 전환 (PDA/프린터)

Woosim→Bixolon 프린터, 기존PDA→Honeywell PDA 전환에서 하드웨어 인터페이스 차이 발생.

| 오류 번호 | 오류명 | 핵심 원인 | 재발 가능성 |
|:---------:|--------|-----------|:----------:|
| 07 | M0라벨 텍스트품질저하 비트맵렌더링 | Bixolon에서 프린터 내장 폰트 대신 앱 비트맵 렌더링 사용 → 품질 저하 | **높음** |
| 10 | TextWatcher 수기입력시 자동실행 문제 | Honeywell Keyboard Wedge 대응 TextWatcher가 수기 입력도 300ms 후 자동실행 | **중간** |
| 13 | Honeywell 바코드 BroadcastReceiver Action 불일치 | Action 문자열이 실제 PDA와 불일치하여 수신 불가 | **높음** |

**공통 특징**: 신규 기기의 통신 프로토콜, 명령어 체계, 데이터 수신 방식이 기존 기기와 다름.

---

### 패턴 F: UI/로직 버그 (기존 코드 또는 신규 코드)

원본에서부터 존재하거나, 리팩토링/테스트 중 발생한 로직 버그. 하드코딩 잔존 포함.

| 오류 번호 | 오류명 | 핵심 원인 | 원본 버그 여부 | 재발 가능성 |
|:---------:|--------|-----------|:------------:|:----------:|
| 01 | 계근완료후 동일바코드 라벨재출력 | dup 결과 미사용 + return 누락 | YES (원본 주석처리) | **낮음** |
| 02 | WH_AREA null체크 OR연산자 버그 | `\|\|`를 `&&`로 변경 필요 (12곳) | YES | **중간** |
| 06 | 바코드매칭실패 BARCODEGOODS위치설정불일치 | 테스트 데이터 위치 설정과 BARCODEGOODS 자릿수 불일치 | NO (테스트데이터 문제) | **낮음** |
| 11 | LoginActivity 종료버튼 프린터테스트 호출 | 테스트용 printTest() 코드가 원복되지 않음 | NO (테스트 코드 잔류) | **낮음** |
| 18 | refreshShipmentList AND/OR 연산자 버그 | 삭제 대상 AND 연결 (OR이어야 함) | YES | **낮음** |
| 24 | PDA 로그인 창고Spinner 하드코딩 삼일냉장 노출 | 하드코딩 fallback("삼일냉장"/"1")이 CO_창고관리 PDA여부 미설정으로 인한 0건 조회를 은폐 | NO (전환 환경 데이터 미설정 + 하드코딩 잔존) | **중간** |
| 28 | setBarcodeMsg 디바운스 바코드값 미비교 연속스캔 삼킴 | Honeywell 이중입력 방지용 디바운스가 시간만 비교 → 다른 바코드·의도된 재귀 호출 차단, 계근 2건 중 1건 누락 | NO (기기 전환 중 신규 추가 코드) | **높음** |
| 29 | 창고목록조회 원인불일치 안내문구 | 통신 실패와 데이터 0건이 동일한 빈 문자열로 수렴 → "ERP 설정 미비"로 원인이 확정된 안내 문구 표시 | NO (오류 24 수정 시 신규 추가된 로직) | **중간** |
| 31 | 이마트 소숫점 반올림 주석 버림동작 불일치 | Math.floor(버림) 연산인데 주석/javadoc은 "반올림"으로 표기, 동작 자체는 원본과 100% 동일 | YES (원본 원문 주석 동일) | **낮음** |

**공통 특징**: 논리 연산자 오류(OR/AND), 조건 분기 누락, 테스트 코드 잔류, 하드코딩 잔존, 표기(주석) 불일치 등.

> 참고: 18번은 패턴 D(GI_D_ID 관련)와도 연관되지만, 근본 원인이 AND/OR 논리 오류이므로 F에도 분류.
> 참고: 28번은 패턴 E(기기 전환 중 추가된 코드)와도 연관되지만, 근본 원인이 디바운스 조건 로직 오류이므로 F에 분류.
> 참고: 31번은 기능적 결함이 아닌 주석/문서 표기 불일치이며, 원본과 동작이 100% 동일하므로 코드 수정 대상이 아니다(표기 정정만 권고).

### 패턴 G: 인코딩/파싱 (데이터 전송/파싱 구조 문제)

앱-서버 간 데이터 인코딩 불일치, Java split 동작 특성으로 인한 파싱 오류.

| 오류 번호 | 오류명 | 핵심 원인 | 재발 가능성 |
|:---------:|--------|-----------|:----------:|
| 03 | search_warehouse 한글깨짐 인코딩불일치 | 앱 EUC-KR 인코딩 → 서버 UTF-8 디코딩 불일치 | **높음** |
| 05 | JSP 마지막컬럼 빈값 파싱오류 | split("::")이 trailing empty string 제거 → ArrayIndexOutOfBounds | **높음** |
| 19 | SM_출고계근 회사코드 ITEM_CODE 잘림오류 | packet splitData 인덱스와 JSP pstmt 매핑 불일치 | **높음** |
| 30 | 빈응답 split ArrayIndexOutOfBoundsException 상시발생 | receiveData가 완전히 빈 문자열일 때 split(";;")/split("::",-1) 결과가 length=1이 되어 result.length>0 가드가 무력화 → temp[1] 이상 접근 시 예외, 조회 0건마다 상시 재현 | **높음** |

> 참고: 19번은 패턴 A(DB 타입 불일치)와도 연관 (VARCHAR(2)에 10자리 저장). 근본 원인이 packet 매핑 오류이므로 G에도 분류.
> 참고: 30번은 05번(마지막 컬럼 빈값)과 유사하나, 05번은 "일부 컬럼 값이 빈 경우"이고 30번은 "응답 전체가 빈 경우"로 원인이 구분된다.

**공통 특징**: 앱-서버 간 데이터 직렬화/역직렬화에서 인코딩, 구분자 처리, 인덱스 매핑 오류.

## 4. 서브 에이전트 활용

### error-doc (오류 문서 작성 에이전트)

오류 문서 작성 시 아래 패턴 번호를 `## 패턴` 섹션에 명시한다.

```markdown
## 패턴
- **패턴 A**: DB 타입 불일치
- 관련 오류: 14번, 19번
```

**패턴별 문서 작성 시 포함 필수 항목:**

| 패턴 | 필수 확인 항목 |
|:----:|---------------|
| A | MSSQL 컬럼 타입, Java 파싱 코드(parseInt/parseDouble), 값 형식 |
| B | Oracle 테이블명, MSSQL 대체 테이블명, JSP SQL 전문 |
| C | Oracle 컬럼 vs MSSQL 컬럼 매핑표, JOIN 구조 차이 |
| D | GI_D_ID 사용처 전수 목록, GI_L_ID 추가 필요 여부 |
| E | 원본 기기 명령어 vs 신규 기기 명령어, 프로토콜 차이 |
| F | 원본 코드 비교, 원본 버그 여부 (YES/NO), 하드코딩 잔존 여부 |
| G | 앱 인코딩, 서버 인코딩, split 옵션, packet 인덱스 매핑표 |

### code-verifier (코드 검증 에이전트)

코드 검증 시 아래 패턴별 체크 항목을 자동 검사한다.

#### 패턴 A 체크
```
- [ ] Integer.parseInt() 호출부에서 입력값이 FLOAT("2.0" 등)일 가능성 확인
- [ ] JSP INSERT 컬럼의 VARCHAR 크기와 packet 데이터 길이 비교
- [ ] datetime 타입 컬럼을 CONVERT(VARCHAR(8), ..., 112) 없이 SELECT하고 있지 않은지 확인
- [ ] NULL 허용 숫자 컬럼 parseDouble/parseInt 전 null/빈문자열/"null" 방어 확인
```

#### 패턴 B 체크
```
- [ ] JSP SQL에서 사용하는 테이블명이 MSSQL에 존재하는지 확인
- [ ] Oracle VIEW 이름이 JSP에 남아있지 않은지 확인
```

#### 패턴 C 체크
```
- [ ] JSP SELECT 컬럼과 Java 파싱 인덱스(temp[N]) 일치 확인
- [ ] JOIN 구조가 Oracle VIEW와 동일한 결과를 반환하는지 확인
- [ ] INSERT 컬럼 목록과 CREATE TABLE 컬럼 목록 비교 (누락 확인)
- [ ] Oracle DECODE/NVL로 NULL default 처리하던 컬럼이 MSSQL 전환 시 빈 문자열까지 방어하고 있는지 확인 (ISNULL+NULLIF 조합)
- [ ] LEFT JOIN 대상 테이블에 1:N 관계 발생 가능성 확인 (Cartesian product 위험)
- [ ] 년월(월별)로 행이 나뉘는 VIEW를 JOIN할 때 년월 조건이 누락되지 않았는지 확인
- [ ] JSP 내 동일 컬럼명 대소문자 혼용 여부 확인 (MSSQL CS 콜레이션 대비)
```

#### 패턴 D 체크
```
- [ ] GI_D_ID를 WHERE 조건으로 사용하는 곳에 GI_L_ID 조건 추가 여부 확인
- [ ] GI_D_ID로 equals 비교하는 곳에 GI_L_ID 조합 비교 추가 여부 확인
- [ ] GI_L_ID가 INSERT에 포함되어 있는지 확인
- [ ] JSP가 GI_L_ID(SM_출고LOT.SEQ 등)를 SELECT/전송하고 있는지, 파싱 클래스에 해당 searchType 분기가 존재하는지 확인 (35번)
```

#### 패턴 E 체크
```
- [ ] BroadcastReceiver Action 문자열이 실제 기기와 일치하는지 확인
- [ ] 프린터 명령어(SLCS V/LD/TD)가 대상 기기에서 지원되는지 확인
- [ ] TextWatcher 등 신규 추가 코드가 기존 입력 흐름에 간섭하지 않는지 확인
- [ ] 디바운스/중복방지 로직이 msg 값 비교 없이 시간만으로 차단하고 있지 않은지 확인 (28번)
```

#### 패턴 F 체크
```
- [ ] null 체크 조건에서 ||와 && 사용이 올바른지 확인
- [ ] if 분기 후 return 누락 여부 확인 (특히 완료 분기)
- [ ] 테스트용 코드(printTest 등)가 남아있지 않은지 확인
- [ ] AND/OR 연산자가 올바른지 확인 (DELETE WHERE 등)
- [ ] 조회 0건 시 하드코딩 fallback이 발동되어 실제 오류를 은폐하지 않는지 확인
- [ ] 신규 추가한 디바운스 블록이 원본의 재귀 호출 경로를 차단하지 않는지 확인 (28번)
- [ ] 통신 실패와 데이터 0건이 동일한 값으로 수렴되어 원인 불일치 안내 문구가 표시되지 않는지 확인 (29번)
- [ ] 주석/javadoc 표기가 실제 연산(Math.floor 등)과 일치하는지 확인, 불일치 시 원본 동일 여부부터 확인 (31번)
```

#### 패턴 G 체크
```
- [ ] split("::")에 -1 옵션 적용 여부 확인
- [ ] HttpHelper 인코딩이 UTF-8인지 확인
- [ ] packet splitData 인덱스와 JSP pstmt 인덱스 매핑 일치 확인
- [ ] receiveData.isEmpty() 가드 없이 split(";;") 결과의 length>0만으로 파싱을 진행하고 있지 않은지 확인 (30번, 빈 문자열도 length=1이 되어 가드 무력화)
```
