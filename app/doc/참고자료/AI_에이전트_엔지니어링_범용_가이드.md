# AI 에이전트 엔지니어링 범용 가이드

**작성일**: 2026-04-08
**목적**: AI 에이전트와 협업하는 프로젝트에서 필요한 엔지니어링 개념, 문서 폴더 체계 설계, 서브에이전트 연동까지를 정리한 범용 가이드

---

## 1. 엔지니어링 개념 정의

### 1.1 프롬프트 엔지니어링 (Prompt Engineering)

AI에게 **무엇을 시킬지 지시하는 기술**이다.
한 번의 대화에서 좋은 질문, 좋은 지시를 내려서 원하는 결과를 얻는 것에 초점을 맞춘다.

예시: 명확한 지시문 작성, 단계별 작업 분해 요청, 출력 형식 지정, 제약 조건 명시

### 1.2 컨텍스트 엔지니어링 (Context Engineering)

AI가 작업할 때 **어떤 정보를 보고 있는가를 설계하는 것**이다.

AI 모델에는 컨텍스트 윈도우라는 한정된 공간이 있다. 이 공간에 무엇을 넣고, 무엇을 빼고, 어떤 순서로 배치하느냐에 따라 결과 품질이 달라진다. 아무리 좋은 질문을 해도 AI가 잘못된 정보를 보고 있으면 잘못된 결과가 나온다.

실무 적용:
- **시스템 프롬프트 설계**: CLAUDE.md, .cursorrules 등에 프로젝트 원칙과 규칙을 정의하여 AI가 세션 시작 시 핵심 맥락을 먼저 인식하게 한다
- **정보 구조화**: 문서를 폴더별로 분류하고 명확한 네이밍 컨벤션을 적용하여 AI가 필요한 정보를 빠르게 찾을 수 있게 한다
- **제약 조건 주입**: 작업 문서마다 AI가 지켜야 할 규칙을 명시하여 해당 작업의 컨텍스트에 직접 제약을 심는다

### 1.3 컴파운드 엔지니어링 (Compound Engineering)

AI 에이전트의 작업 루프에 **"종합(Compound)" 단계를 추가**하는 것이다.

기존 워크플로우:
```
Plan → Work → Review (루프) → 완료
```

컴파운드 엔지니어링 적용:
```
Plan → Work → Review (루프) → Compound → 완료
```

Compound 단계에서는 실행/검토 루프 중 발생했던 모든 에러와 문제점을 종합해서 시스템 프롬프트 파일에 기록한다. 다음 작업 시 AI가 그 기록을 참고하여 **동일한 실수를 반복하지 않게** 된다.

핵심 원칙: **AI의 실수는 한 번으로 족하다.**

Compound 단계 실행 방법:
- **자동화**: 서브에이전트, Custom Slash Commands 등을 통해 에러 패턴 분석 및 시스템 프롬프트 반영을 자동화
- **수동**: 작업 완료 후 AI에게 직접 지시 — "지금까지 발생했던 에러를 정리해서 다시 발생하지 않도록 기록해줘"

### 1.4 하네스 엔지니어링 (Harness Engineering)

AI 에이전트를 효과적으로 제어하고 활용하기 위한 **전체적인 체계를 설계하는 것**이다.

"Harness"는 원래 말에 채우는 마구(馬具)로, 말의 힘을 통제하고 원하는 방향으로 이끌기 위한 장치이다. AI에 적용하면, AI의 능력을 원하는 방향으로 정확하게 쓰이도록 제어하는 모든 것을 의미한다.

프롬프트 엔지니어링, 컨텍스트 엔지니어링, 컴파운드 엔지니어링을 모두 포괄하는 상위 개념이다.

### 1.5 개념 간 관계

```
하네스 엔지니어링 (전체 제어 체계)
    ├── 컨텍스트 엔지니어링 (AI에게 무엇을 보여줄지 설계)
    ├── 프롬프트 엔지니어링 (AI에게 무엇을 시킬지 지시)
    └── 컴파운드 엔지니어링 (에러 패턴을 컨텍스트에 자동 누적)
```

| 개념 | 초점 | 범위 | 시점 |
|------|------|------|------|
| 프롬프트 엔지니어링 | 지시의 질 | 단일 대화 | 작업 중 |
| 컨텍스트 엔지니어링 | 정보의 질 | 프로젝트 전체 | 작업 전 |
| 컴파운드 엔지니어링 | 학습의 질 | 스프린트 간 | 작업 후 |
| 하네스 엔지니어링 | 제어의 질 | 전체 | 상시 |

## 2. 문서 폴더 체계 설계

### 2.1 설계 원칙

AI 에이전트는 사람과 다르게 정보를 탐색한다. 사람은 기억과 경험으로 추측할 수 있지만, AI 에이전트는 매 세션마다 새로 시작한다. 따라서 문서 체계는 다음을 만족해야 한다:

- **시스템 프롬프트 한 곳만 읽으면** 프로젝트 전체 구조를 파악할 수 있어야 한다
- **폴더명과 문서명만 보고** 내용을 예측할 수 있어야 한다
- **문서 간 참조 관계가 명시적**이어야 한다 (AI는 "암묵적으로 알고 있는 것"이 없다)
- **템플릿이 존재**해야 한다 (일관된 형식은 AI의 파싱 정확도를 높인다)

### 2.2 권장 폴더 구조

```
프로젝트/
    ├── CLAUDE.md (또는 .cursorrules 등 시스템 프롬프트)
    ├── .claude/
    │   └── agents/              # 서브에이전트 정의
    │       ├── compound.md
    │       ├── doc-writer.md
    │       └── code-reviewer.md
    └── doc/
        ├── README.md            # 문서 체계 안내 (선택)
        ├── 오류/                # 오류 선문서화
        ├── 개발/                # 개발 작업 문서
        ├── 테스트/              # 테스트 시나리오
        ├── 테스트데이터/         # 테스트에 사용한 데이터 기록
        ├── 기능/                # 기능 동작 정리
        ├── 소스분석/            # 파일별 소스 분석
        ├── 일정/                # 일별 작업 일정
        └── 참고자료/            # 매뉴얼, 참고 자료
```

### 2.3 폴더별 역할과 엔지니어링 매핑

| 폴더 | 역할 | 관련 엔지니어링 |
|------|------|:-------------:|
| 오류/ | 오류 발생 시 **수정 전에 먼저 문서화**. 에러의 원인, 영향 범위, 수정 방안을 기록 | 컴파운드 |
| 개발/ | 개발 작업 문서. 현재 구조 → 변경 구조 → Step별 플랜 → 진행 현황 기록 | 프롬프트 |
| 테스트/ | 테스트 시나리오. 절차, 확인 항목, 통과/실패 상태를 기록 | 프롬프트 |
| 테스트데이터/ | 테스트에 사용한 데이터를 기록. 재현 가능성 확보 | 컨텍스트 |
| 기능/ | 프로그램 기능의 전체 흐름과 분기 동작을 정리 | 컨텍스트 |
| 소스분석/ | 파일별 역할, 메서드, 호출 관계, 데이터 흐름을 분석 | 컨텍스트 |
| 일정/ | 일별 작업 대상, 완료 기록, 커밋 이력 관리 | 하네스 |
| 참고자료/ | 매뉴얼, 가이드, 외부 참고 자료 | 컨텍스트 |

### 2.4 폴더별 참조 관계

```
                    ┌─────────────┐
                    │   일정/      │
                    │  (일별 관리)  │
                    └──────┬──────┘
                           │ 참조
                    ┌──────▼──────┐
               ┌───►│   개발/      │◄───┐
               │    │  (작업 문서)  │    │
               │    └──┬───┬──────┘    │
               │       │   │           │
        ┌──────┴───┐   │   │    ┌──────┴──────┐
        │   오류/   │   │   │    │  소스분석/   │
        │ (에러기록) │◄──┘   │    │  (코드 분석) │
        └──────┬───┘       │    └──────┬──────┘
               │           │           │
               │    ┌──────▼──────┐    │
               └───►│  테스트/     │◄──┘
                    │ (시나리오)    │
                    └──────┬──────┘
                           │ 참조
                    ┌──────▼──────┐
                    │ 테스트데이터/ │
                    │ (데이터 기록) │
                    └─────────────┘

        ┌─────────────┐        ┌─────────────┐
        │   기능/      │◄──────►│  소스분석/   │
        │ (기능 정리)   │ 상호참조 │  (코드 분석) │
        └─────────────┘        └─────────────┘
```

핵심 순환 흐름:
```
오류/ → 개발/ → 테스트/ → 오류/ (재발 시) → Compound (패턴 반영)
```

| 폴더 | 참조하는 폴더 | 참조받는 폴더 |
|------|:----------:|:----------:|
| 오류/ | - | 개발/ |
| 개발/ | 오류/, 소스분석/, 기능/ | 일정/ |
| 테스트/ | 테스트데이터/ | 오류/ (실패 시) |
| 테스트데이터/ | - | 테스트/ |
| 소스분석/ | 기능/, 오류/ | 개발/ |
| 기능/ | 소스분석/ | 개발/ |
| 일정/ | 개발/, 오류/ | - |
| 참고자료/ | - | - |

## 3. 문서 규칙

### 3.1 문서명 네이밍 컨벤션

```
순번_문서명[관련문서명(조건부)].md
```

| 폴더 | 형식 | 예시 |
|------|------|------|
| 오류/ | `순번_오류명[테스트시나리오명].md` | `05_JSP_파싱오류.md` |
| 개발/ | `순번_개발명[오류명].md` | `12_파싱수정[JSP_파싱오류].md` |
| 테스트/ | `순번_테스트시나리오명.md` | `01_출하대상받기.md` |
| 테스트데이터/ | `순번_테스트데이터명.md` | `01_출하테스트데이터.md` |
| 기능/ | `순번_기능명.md` | `03_바코드스캔_프로세스.md` |
| 소스분석/ | `순번_분석명.md` | `08_HttpHelper.md` |
| 일정/ | `YYYY-MM-DD.md` | `2026-04-08.md` |

### 3.2 템플릿 규칙

- 각 폴더에 `00_*_템플릿.md` 파일을 둔다
- 새 문서 작성 시 반드시 템플릿을 기반으로 작성한다
- 모든 문서에는 **"관련 문서"** 섹션을 포함하고, 참조하는 다른 폴더의 문서 경로를 명시한다

### 3.3 핵심 규칙: 오류 선문서화

**오류가 발생하면 바로 수정하지 않고 반드시 먼저 문서화한다.**

이것이 컴파운드 엔지니어링의 기반이다. 오류를 문서화하지 않으면:
- 같은 에러가 반복되어도 AI가 인식하지 못한다
- 에러 패턴을 분석할 수 없다
- 시스템 프롬프트에 반영할 데이터가 없다

## 4. 시스템 프롬프트(CLAUDE.md) 필수 포함 항목

시스템 프롬프트는 AI 에이전트가 세션 시작 시 가장 먼저 읽는 파일이다. 다음 항목이 포함되어야 4개 엔지니어링이 모두 작동한다.

| AI 도구 | 시스템 프롬프트 파일 |
|---------|-------------------|
| Claude Code | CLAUDE.md |
| Cursor | .cursorrules |
| Codex | codex.md |
| OpenCode | opencode.md |

### 4.1 구성 항목과 엔지니어링 매핑

```markdown
# 프로젝트명

## 핵심 원칙                    ← 하네스 (최우선 제약)
## AI 제약 조건                  ← 프롬프트 (AI 행동 규칙)
## 프로젝트 목적                 ← 컨텍스트 (배경 정보)
## 프로젝트 개요                 ← 컨텍스트 (기술 스택 등)
## 문서 폴더 정의                ← 컨텍스트 (정보 탐색 지도)
## 문서 폴더 간 참조 관계         ← 컨텍스트 (관계 구조)
## 개발 프로세스 흐름             ← 하네스 + 컴파운드 (작업 순서 강제)
## 문서 작성 규칙                ← 프롬프트 (형식 규칙)
## 주요 파일 경로                ← 컨텍스트 (경로 정보)
## 알려진 버그 및 에러 패턴       ← 컴파운드 (누적 학습 대상)
## 커밋 규칙                    ← 프롬프트 (출력 형식)
## 외부 프로젝트 경로             ← 컨텍스트 (외부 참조)
```

### 4.2 핵심 원칙 (하네스)

프로젝트에서 절대 위반하면 안 되는 최상위 규칙.

```markdown
## 핵심 원칙
- 기존 기능과 100% 동일하게 동작해야 한다
- 사용자 데이터 손실이 발생하면 안 된다
- (프로젝트별 최우선 원칙)
```

### 4.3 AI 제약 조건 (프롬프트)

AI가 작업 시 지켜야 할 행동 규칙. **이 섹션이 시스템 프롬프트에 없으면, AI가 개발 문서를 열기 전까지 규칙을 인지하지 못한다.**

```markdown
## AI 제약 조건
- 기존 로직을 임의로 제거/추가/변경하지 않는다
- 문서에 명시된 step만 진행하고, 다음 step은 지시를 기다린다
- step 완료 후 체크리스트 및 진행 현황을 반드시 업데이트한다
- 문서에 없는 개선/리팩토링을 임의로 수행하지 않는다
```

### 4.4 개발 프로세스 흐름 (하네스 + 컴파운드)

**Compound 단계를 포함**한 전체 작업 순서. 이 흐름이 시스템 프롬프트에 있어야 AI가 작업 완료 후 Compound 단계를 수행해야 한다는 것을 인지한다.

```markdown
## 개발 프로세스 흐름

오류/ → 개발/ → 테스트/ → 오류/ (재발 시) → Compound (패턴 반영)

1. 오류 발견 → 오류/ 문서화 (수정 전 반드시 선문서화)
2. 개발/ 문서 작성 후 코드 수정
3. 테스트/ 시나리오 동작 확인
4. 테스트 중 오류 발생 → 오류/ 다시 문서화
5. 작업 완료 → Compound: 에러 패턴 분석 및 "알려진 버그" 섹션 반영
```

### 4.5 알려진 버그 및 에러 패턴 (컴파운드)

Compound 단계에서 누적되는 섹션. 이 섹션이 시스템 프롬프트에 있어야 AI가 다음 작업에서 같은 실수를 방지한다.

```markdown
## 알려진 버그 및 에러 패턴

### 미수정 버그
1. `오류문서경로` - 버그 요약

### 에러 패턴 (Compound 누적)
1. [패턴명]: 설명 — 관련 오류 N건
   - 예방 규칙: 해당 유형 코드 수정 시 주의할 점
```

## 5. 서브에이전트 연동

### 5.1 서브에이전트란

Claude Code에서 사용자가 직접 만들 수 있는 특화된 AI 어시스턴트이다. 각 서브에이전트는 자체 컨텍스트 윈도우에서 실행되며, 사용자 정의 시스템 프롬프트, 특정 도구 액세스, 독립적인 권한, 지속적 메모리를 가진다.

참고 문서: https://code.claude.com/docs/ko/sub-agents

### 5.2 생성 방법

**방법 1: 대화형 인터페이스**
```
Claude Code에서 /agents 실행
→ Create new agent 선택
→ Personal 또는 Project 선택
→ 설명 입력 후 Claude가 자동 생성
```

**방법 2: 마크다운 파일 직접 생성**

파일 위치:
- 프로젝트 전용: `.claude/agents/에이전트명.md`
- 모든 프로젝트 공용: `~/.claude/agents/에이전트명.md`

파일 형식:
```yaml
---
name: 에이전트-이름
description: 에이전트 설명 (Claude가 위임 시기를 결정하는 데 사용)
tools: Read, Grep, Glob, Edit, Bash
model: sonnet
memory: project
---

여기에 시스템 프롬프트를 작성한다.
에이전트가 호출되었을 때 어떻게 동작해야 하는지 정의한다.
```

**방법 3: CLI 플래그**
```bash
claude --agents '{
  "에이전트명": {
    "description": "설명",
    "prompt": "시스템 프롬프트",
    "tools": ["Read", "Grep"],
    "model": "sonnet"
  }
}'
```

### 5.3 주요 설정 항목

| 항목 | 필수 | 설명 |
|------|:----:|------|
| name | 예 | 소문자 및 하이픈 사용한 고유 식별자 |
| description | 예 | Claude가 위임 시기 결정에 사용하는 설명 |
| tools | 아니오 | 사용 가능한 도구 제한. 생략 시 모든 도구 상속 |
| model | 아니오 | sonnet, opus, haiku, inherit 중 선택. 기본값: inherit |
| memory | 아니오 | user, project, local 중 선택. 세션 간 학습 누적 활성화 |
| permissionMode | 아니오 | default, acceptEdits, auto, bypassPermissions 등 |
| maxTurns | 아니오 | 최대 에이전트 턴 수 제한 |
| background | 아니오 | true 설정 시 백그라운드에서 병렬 실행 |

### 5.4 지속적 메모리

서브에이전트에 `memory` 필드를 설정하면 대화 간에 지식이 누적된다. 이것이 컴파운드 엔지니어링 자동화의 핵심이다.

| 범위 | 저장 위치 | 용도 |
|------|----------|------|
| user | `~/.claude/agent-memory/에이전트명/` | 모든 프로젝트 간 학습 누적 |
| project | `.claude/agent-memory/에이전트명/` | 프로젝트별 학습 (Git 공유 가능) |
| local | `.claude/agent-memory-local/에이전트명/` | 프로젝트별 학습 (Git 비공유) |

### 5.5 서브에이전트와 폴더 체계의 관계

각 서브에이전트는 특정 폴더를 주요 작업 대상으로 가진다.

```
compound 에이전트      → 오류/ (읽기) → CLAUDE.md (쓰기)
doc-writer 에이전트    → 각 폴더의 템플릿 (읽기) → 각 폴더 (쓰기)
code-reviewer 에이전트 → 소스분석/, 기능/ (읽기)
```

### 5.6 범용 서브에이전트 예시

#### compound (컴파운드 에이전트)

에러 패턴을 분석하고 시스템 프롬프트에 반영한다.

```yaml
---
name: compound
description: 에러 패턴을 분석하고 시스템 프롬프트에 반영하는 컴파운드 에이전트. 개발/검토 루프 완료 후 사용.
tools: Read, Grep, Glob, Edit
memory: project
model: inherit
---

당신은 컴파운드 엔지니어링을 수행하는 에이전트입니다.

호출되면 다음을 수행합니다:

1. 오류/ 폴더의 전체 에러 문서를 스캔합니다
2. 각 에러의 원인, 영향 범위, 수정 방안을 분석합니다
3. 반복되는 패턴을 식별합니다
   - 동일 모듈에서 반복되는 에러
   - 동일 유형의 에러 (파싱, 타입, null 처리 등)
   - 동일 원인에서 파생되는 에러
4. 시스템 프롬프트 파일(CLAUDE.md)의 "알려진 버그 및 에러 패턴" 섹션에 반영합니다
5. 에이전트 메모리에 분석 결과를 기록합니다

기록 형식:
- 패턴명: [간결한 패턴 설명]
- 발생 빈도: N건
- 관련 에러: [에러 문서 목록]
- 예방 규칙: [다음 작업에서 지켜야 할 규칙]

주의사항:
- 이미 반영된 패턴은 중복 추가하지 않습니다
- 수정 완료된 버그는 미수정 목록에서 제거합니다
- 에이전트 메모리를 확인하여 이전 분석과 비교합니다
```

#### doc-writer (문서 작성 에이전트)

프로젝트 문서를 템플릿에 맞게 자동 생성한다.

```yaml
---
name: doc-writer
description: 프로젝트 문서를 템플릿에 맞게 생성하는 에이전트. 오류/개발/기능/소스분석/테스트 등 문서 작성 시 사용.
tools: Read, Write, Glob, Grep
model: haiku
---

당신은 문서 작성 에이전트입니다.

호출되면 다음을 수행합니다:

1. 사용자가 지정한 대상 폴더를 확인합니다
2. 해당 폴더의 기존 문서 목록을 스캔하여 마지막 순번을 확인합니다
3. 해당 폴더의 00_*_템플릿.md 파일을 읽습니다
4. 템플릿 형식대로 새 문서를 생성합니다
   - 순번: 마지막 번호 + 1
   - 문서명: 폴더별 네이밍 컨벤션 준수
   - 관련 문서: 참조 관계에 맞는 문서 경로 자동 기입
5. 생성 결과를 보고합니다

규칙:
- 템플릿의 모든 섹션을 유지합니다
- 관련 문서 경로는 실제 존재하는 문서만 기입합니다
- 사용자가 제공한 정보로 채울 수 있는 섹션만 채우고, 나머지는 템플릿 상태로 둡니다
```

#### code-reviewer (코드 리뷰 에이전트)

코드 변경사항을 검토하고 품질/보안 이슈를 보고한다.

```yaml
---
name: code-reviewer
description: 코드 변경사항을 검토하는 에이전트. 코드 수정 후 품질/보안 확인 시 사용.
tools: Read, Grep, Glob, Bash
model: inherit
---

당신은 시니어 코드 리뷰어입니다. 코드를 수정하지 않고 검토만 합니다.

호출되면 다음을 수행합니다:

1. git diff로 최근 변경사항을 확인합니다
2. 변경된 파일에 집중하여 검토합니다

검토 체크리스트:
- 코드가 명확하고 읽기 쉬운가
- 중복 코드가 없는가
- 에러 핸들링이 적절한가
- 보안 이슈가 없는가
- 기존 기능에 영향을 주지 않는가

피드백 우선순위:
- Critical: 반드시 수정 필요
- Warning: 수정 권장
- Suggestion: 개선 고려
```

## 6. 워크플로우 설계

### 6.1 전체 워크플로우

```
[작업 시작]
    ↓
Plan: 개발/ 문서 작성 ─── doc-writer 에이전트 활용 가능
    ├── 현재 구조 파악
    ├── 변경 구조 설계
    ├── Step별 개발 플랜 수립
    └── AI 제약 조건 명시
    ↓
Work: 코드 수정 (Step별 진행)
    ├── Step 완료 후 체크리스트 업데이트
    └── 커밋 (규칙에 맞는 메시지)
    ↓
Review: 검토 ─── code-reviewer 에이전트 활용 가능
    ├── 코드 리뷰
    └── 테스트 시나리오 실행
    ↓
오류 발생 시 → 오류/ 문서화 ─── doc-writer 에이전트 활용 가능
    │                              → Work로 복귀
    ↓
Compound: 에러 패턴 종합 ─── compound 에이전트 실행
    ├── 오류/ 폴더 스캔
    ├── 패턴 분석
    ├── CLAUDE.md 반영
    └── 에이전트 메모리 업데이트
    ↓
[작업 완료 — 다음 세션에서 AI가 에러 패턴을 사전 인지]
```

### 6.2 Compound 단계의 중요성

Compound 단계가 없으면:
```
세션 1: 에러 A 발생 → 수정
세션 2: 에러 A 재발생 → 다시 수정
세션 3: 에러 A 또 재발생 → 또 수정
```

Compound 단계가 있으면:
```
세션 1: 에러 A 발생 → 수정 → Compound (패턴 기록)
세션 2: 에러 A 패턴을 인지 → 사전 방지
세션 3: 새로운 에러 B 발생 → 수정 → Compound (패턴 추가)
```

시스템 프롬프트에 누적되는 에러 패턴이 많아질수록 AI의 실수는 줄어든다. 이것이 "복합(Compound)" 효과이다.

### 6.3 자동화 수준별 도입 단계

서브에이전트를 한꺼번에 도입할 필요는 없다. 단계적으로 도입한다.

**1단계: 수동 Compound (서브에이전트 없이)**

작업 완료 후 AI에게 직접 지시:
```
지금까지 발생했던 에러를 분석해서 CLAUDE.md의 "에러 패턴" 섹션에 반영해줘.
```

이 단계에서는 폴더 체계와 시스템 프롬프트만 갖추면 된다.

**2단계: compound 에이전트 도입**

가장 임팩트가 큰 에이전트를 먼저 도입한다. 작업 완료 후 compound 에이전트를 호출하면 자동으로 에러 패턴을 분석하고 시스템 프롬프트에 반영한다. 지속적 메모리(memory: project)를 통해 세션 간 지식이 누적된다.

**3단계: doc-writer, code-reviewer 도입**

반복적인 문서 생성과 코드 리뷰를 자동화한다. 이 단계에서는 워크플로우의 대부분이 서브에이전트를 통해 수행된다.

**4단계: 프로젝트 맞춤 에이전트 추가**

프로젝트 특성에 따라 추가 에이전트를 만든다:
- 원본 비교 에이전트 (마이그레이션/전환 프로젝트)
- 테스트 시나리오 생성 에이전트
- 일정 관리 에이전트
- 배포 체크리스트 에이전트

## 7. 템플릿 가이드

### 7.1 오류 문서 템플릿

오류 문서는 컴파운드 엔지니어링의 핵심 입력이다. 다음 항목이 반드시 포함되어야 compound 에이전트가 패턴을 분석할 수 있다.

```markdown
# [오류 제목]

## 발견일
YYYY-MM-DD

## 에러 발생 시나리오
1. 사전 동작
2. 사용자 조작
3. 에러 발생 시점
4. 에러 결과

## 현상
- 현상 설명

## 원인
### 문제 1: [원인 요약]
- 코드 위치: `파일명:라인`
- 문제 코드
- 발생 시나리오

## 영향 범위
- 영향받는 파일/기능 목록

## 수정 방안
- 수정 후 코드

## 상태
- [ ] 미수정

## 관련 문서
- `doc/개발/문서명.md`
```

### 7.2 개발 문서 템플릿

개발 문서는 AI 에이전트의 작업 지시서이다. AI 제약 조건과 Step별 체크리스트가 핵심이다.

```markdown
# [제목]

**작성일**: YYYY-MM-DD
**목적**: [이 문서의 목적]

## AI 제약 조건
- 기존 로직을 임의로 제거/추가/변경하지 않는다
- 문서에 명시된 step만 진행하고, 다음 step은 지시를 기다린다
- step 완료 후 체크리스트를 반드시 업데이트한다
- 문서에 없는 개선/리팩토링을 임의로 수행하지 않는다

## 1. 현재 구조
(현재 코드/동작 설명)

## 2. 변경 구조
(목표 코드/동작 설명)

## 3. 수정 대상 파일
| # | 파일 | 위치 | 수정 내용 |
|:-:|------|------|----------|

## 4. 개발 플랜

### Step 1: [작업명]

**체크리스트**
- [ ] 분석 완료
- [ ] 변환 수행
- [ ] 컴파일 확인
- [ ] 단위테스트
- [ ] 회귀테스트

**변경 내용** (완료 후 작성):
- 무엇을:
- 왜:
- 어떻게:

## 5. 진행 현황
| Step | 작업 | 상태 |
|------|------|------|
| 1 | 작업명 | ⏳ 대기 |

## 관련 문서
- `doc/오류/문서명.md`
```

### 7.3 기타 템플릿

프로젝트 상황에 맞게 테스트, 기능, 소스분석, 일정 등의 템플릿도 동일한 원칙으로 작성한다:
- 모든 템플릿에 **"관련 문서"** 섹션 포함
- 상태 추적 가능한 **체크리스트/상태값** 포함
- AI가 파싱하기 쉬운 **일관된 형식** 유지
